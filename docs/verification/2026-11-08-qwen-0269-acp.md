## Native ACP and permission legs

The unmodified promoted `qwen-acp.py` ran with `--acp --bare --advisor off`,
synthetic OpenAI auth, `fixture-model`, loopback port 9 and telemetry disabled.
No ACP prompt was sent and no model or fixture completion was requested.

- `initialize` returned protocol 1 and exact `qwen-code` / `Qwen Code` / 0.26.9
  identity. Only the expected terminal OpenAI auth method was offered.
- `session/new` returned a nonempty session identity, only the fixture model,
  and initial mode `default`. The advertised ids include the hub's mapped subset
  `default`, `auto-edit`, `yolo`. All four `session/set_mode` calls in
  `default -> auto-edit -> yolo -> default` acknowledged successfully.
- The unchanged preload's positive denial control passed before candidate code.
  Six startup network API attempts were blocked in each run; no connection was
  allowed by the kernel profile. This does not infer absence of attempted calls
  from an empty log.
- `qwen-permission.mjs` drove the actual published `SubAgentTracker` handler,
  using only synthetic clients, tools and events. Two permission requests had
  the exact options: project/user `allow_always`, `proceed_once` / `allow_once`,
  and `cancel` / `reject_once`. The allow-once callback returned `proceed_once`,
  cancellation returned `cancel`, and an unoffered option was rejected. No
  permission-fixture network attempt was recorded. No model-generated tool call
  or actual board approval was involved.
