# Jcode 0.99.1 receipt (#843 AC5)

Date: 2026-10-26. Refs #843. Installed release build, read through `--quiet version --json`: `semver` 0.99.1, `version` `v0.99.1 (7206efd0c)`, from [1jehuang/jcode](https://github.com/1jehuang/jcode) tag v0.99.1 (published 2026-10-22). Host macOS arm64, Bun 1.4.3.

This repeats the ACP, serve and MCP contract legs of [the 0.98.1 receipt](2026-10-19-jcode-0.98.1.md) and the 0.99.0 steering check. Every leg passed, so 0.99.1 is added to jcode `verified` in `src/adapters/compat.ts` in the same change.

## Isolation

- Every process ran under an isolated `HOME` and `JCODE_HOME` (fresh directories under `/tmp/ahub-jc0991`, an empty `mcp.json`, no credentials, no account), with `JCODE_NO_TELEMETRY=1` and `JCODE_DISABLE_CLAUDE_MCP=1` as the adapter sets them. The real `~/.jcode` was never the home.
- SHA-256 of the four real config files that sit directly in `~/.jcode` (`auth.json`, `auth-refresh-state.json`, `config.toml` and `mcp.json`) was taken before the first leg and compared after the last: unchanged.
- The probes built every argv with the adapter's own `jcodeCommand` and spawned `serve` with `JCODE_SOCKET` and `JCODE_READY_FD=3` the way `JcodePeer` does. After each run `pgrep` found no process whose command line named the sandbox, and no telemetry file was written into the isolated home.

## Contract legs (idle server, no model)

- **serve** with the adapter's socket name `j.sock`: ready on the private socket in 102 to 104 ms across two runs. It leaves `j-debug.sock`, `j.sock.hash`, `j.sock.server.json` and `j.sock.daemon.lock` beside it, and the server info file carries `argv`, `debug_socket_path`, `idle_timeout_secs`, `owner_pid`, `pid`, `ppid`, `schema_version`, `scope`, `socket_path` and `started_at`. The process group is gone after SIGTERM.
- **ACP** (`acp --mcp-tools eager` against the same private server):
  - `initialize`: `protocolVersion` 1, `agentInfo` `{ name: "jcode", title: "Jcode", version: "0.99.1" }`, `loadSession: true`, `authMethods: []`.
  - `session/new` returns `configOptions`, `models` and `sessionId`.
  - `session/load` returns `configOptions` and `models` only, with no `sessionId`. The restored identity stays unproven, so `requireLoadSessionEcho` and the withheld automatic recovery are unchanged.
  - `session/set_mode` and `session/request_permission` are still `Unsupported ACP method`, as on 0.98.1.
- **MCP**: a project `.jcode/mcp.json` entry that names no peer was started by the eager ACP child, and its environment held exactly `AGENTHUB_PEER_ID` and `AGENTHUB_LAUNCH_ID` from the owned process environment (values set on the `acp` child by the probe), nothing from the entry itself.
- **Telemetry**: with the adapter's `JCODE_NO_TELEMETRY=1` no telemetry file appeared in the isolated home.

## Steering leg (the 0.99.0 check, now on a running turn)

The 0.99.0 check was established on an idle session. This receipt also exercises it on a running turn, still with no account: the isolated home holds one `openai-compatible` profile `fakegw` (added with `jcode provider add ... --no-api-key`, written only into the isolated `config.toml`) pointing at a local server on `127.0.0.1:18999` that streams a slow, fixed reply and records each request it receives. No real provider, key or model was involved.

- `serve` and `acp` were started with the adapter's argv carrying `--model fake-model --provider-profile fakegw`, a session was created and `session/prompt` started a turn.
- While that turn streamed, a second client on the private socket ran the same steps as `nativeSteer`: `ping` listed `soft_interrupt_ids` in `capabilities`, `subscribe` with `target_session_id` joined the same session (no new session), `state` reported `is_processing: true`, `soft_interrupt` with `urgent: false` was acknowledged.
- The prompt then ended with `end_turn`, not `cancelled`. The local server saw two requests. The first held only the original prompt. The second held the original prompt, the assistant text streamed so far and the steer text as a new user message, so the steer was injected at the end of the running response and the turn was not cancelled, as the adapter's comment on `nativeSteer` states.
- The idle variant (the same ping, subscribe and state steps against an idle session, run in the contract legs above) reports `is_processing: false`, which `nativeSteer` refuses with "the session has no running turn" without sending anything. That refusal is read from the adapter's source; the probe sent no steer to an idle session.

## Source comparison v0.99.0..v0.99.1

232 commits, 300 files, read only through the GitHub compare API (nothing built).

- Protocol (`crates/jcode-protocol`): additions only. `SwarmMemberRuntime` gains four optional fields, `Request::PersistSession` is new, and a swarm send can be refused for a non-coordinator. No existing request, field or `soft_interrupt_ids` capability was removed or renamed.
- MCP (`tool/mcp.rs`): the model-facing `mcp_search` and `mcp_call` tools become internal aliases of `mcp action=search` and `mcp action=call`. The hub's configuration and its injected tools never name those tools, so nothing here changes the owned MCP set.
- No change under the ACP, socket-name or `JCODE_READY_FD` paths was found among the files read; the fixes listed in the release notes (OpenAI schema, TUI recovery from a vanished server, configured model for fresh sessions, stale daemon token recovery) are native behavior behind the same contract.

## Not verified

- A real account, provider or model, and a model turn that calls a hub tool through the project MCP entry, as in every earlier jcode receipt. The steering leg proves delivery to the provider request, not how a real model reacts to it.
- The TUI form (`jcode --resume`), covered separately for 0.98.1 in [the TUI receipt](2026-10-20-jcode-tui-0.98.1.md), was not repeated.
- A second instance running beside the base peer, and Linux or Intel macOS builds.

## Decision

All legs passed, so `0.99.1` joins `verified` for jcode. The accepted range (0.98.0 up to, not including, 1.0.0) is unchanged. A failed leg on a later release would have meant no bump, as the task requires.
